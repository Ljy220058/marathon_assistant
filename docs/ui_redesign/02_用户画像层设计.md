# 用户画像层设计（产品级细化版）

## 1. 文档目的

本文档定义马拉松助手用户画像层的产品级设计。画像层负责把用户基础信息、训练目标、能力水平和风险因素转化为可解释的跑者身份模型，同时承载画像填写与更新的完整体验。

## 2. 模块定位

用户画像层不应只是资料填写表单，而应成为训练计划生成和解释链路的基础。

它需要让用户理解：系统如何看待我，以及这个判断如何影响训练安排。同时，填写画像的过程本身应让用户感到"我在向教练介绍自己"，而不是"我在填一份医院问卷"。

## 3. 用户场景

### 3.1 场景 A：首次使用，完整填写画像

用户第一次进入系统。入口层检测到画像不完整，引导进入画像填写。

用户此时的困惑：
- 为什么要问这么多问题？
- 哪些问题是必填的？
- 我不知道自己的 LTHR 怎么办？

画像层需在此场景下：逐字段引导、解释每个字段的意义、允许跳过非阻塞字段。

### 3.2 场景 B：想快速生成计划

用户不想填完整画像，只想快速拿到一份计划。

用户此时的困惑：
- 最少要填什么？
- 填完能不能马上看到计划？

画像层需在此场景下提供极速模式：只问 3 个阻塞字段（目标、周跑量、可用训练日）。

### 3.3 场景 C：计划已生成，想补充高级信息

用户已拿到计划，但发现系统提示"补充以下信息可获得更个性化计划"。

用户此时的困惑：
- 补充这些信息真的有用吗？
- 怎么只补充缺少的那几个？

画像层需在此场景下提供增量补全入口，且每次只提示缺失字段。

### 3.4 场景 D：训练几周后，状态变化

用户训练了两周，感觉自己变强了，或者受伤了想调整。

用户此时的困惑：
- 我需要主动改画像吗？
- 还是系统会自动发现我变了？

画像层需在此场景下支持手动编辑 + 自动识别（从聊天中 NLP 提取）双通道更新。

## 4. 信息架构

画像层的信息架构分为两层：**填写态**（编辑中）和**展示态**（训练中）。

### 4.1 填写态：画像向导

```text
画像向导
├── 进度指示（如 "📋 训练画像 [5/13]"）
├── 当前字段问题
│   ├── 字段说明（为什么重要）
│   └── 选项 / 输入区
├── 当前已选值预览
└── 操作：返回 / 清空 / 确认
```

### 4.2 展示态：跑者身份卡

```text
跑者身份卡
├── 跑者类型标签（如 "进阶跑者 · 全马 sub330"）
├── 核心指标行
│   ├── 周跑量
│   ├── LTHR
│   └── T配速
├── 训练目标
├── LTHR 九区心率和配速区间
├── 可用训练日
├── 补充信息摘要（收缩态）
└── 编辑入口
```

### 4.3 画像字段分级

| 级别 | 字段 | 阻塞计划生成？ | 填写方式 |
|------|------|:---:|------|
| **一级：硬阻塞** | 目标 (goal) | ✅ | 选项 |
| | 周跑量 (weekly_mileage) | ✅ | 选项 + 自定义 |
| | 可用训练日 (available_days) | ✅ | 多选 |
| **二级：增强** | 经验水平 (experience_level) | ❌ | 选项 |
| | 比赛日期 (target_race_date) | ❌ | 选项 |
| | LTHR | ❌ | 选项 + 自定义 |
| | T配速 (t_pace) | ❌ | 选项 + 自定义 |
| | VO₂max | ❌ | 选项 + 自定义 |
| | 最长训练时长 (max_session_minutes) | ❌ | 选项 |
| | 地形偏好 (terrain_preference) | ❌ | 多选 |
| | 训练类型偏好 (training_types) | ❌ | 多选 |
| | PB 记录 (pb_5k/10k/half/full) | ❌ | 自定义输入 |
| **三级：自动衍生** | 心率九区 (hr_zones) | — | 从 LTHR 自动计算 |
| | 配速区间 (pace_zones) | — | 从 T配速 自动计算 |
| | 训练周期 (plan_duration_weeks) | — | 从比赛日期自动推算 |

## 5. 组件拆分

### 5.1 跑者身份卡（RunnerIdentityCard）

- 位置：训练工作台侧边或会话顶部
- 类型：CustomElement（React 组件）
- 职责：展示态，浓缩展示画像摘要
- 字段：
  - 跑者类型标签
  - 核心指标（周跑量 / LTHR / T配速）
  - 训练目标
  - LTHR 九区心率和配速区间（可折叠）
  - 编辑入口按钮
- 交互：点击编辑按钮 → 进入增量编辑模式
- 可移植性：纯 props 驱动，不依赖 Chainlit 特有 API

### 5.2 画像向导步进器（ProfileStepper）

- 位置：聊天区域主消息
- 类型：cl.Message + cl.Action 组合
- 职责：填写态，逐字段引导用户完成画像
- 展示：
  - 进度条（如 `[████░░░░] 5/13`）
  - 当前字段说明文案
  - 根据字段类型渲染不同输入控件：
    - 单选 → 选项按钮组（cl.Action）
    - 多选 → 切换按钮 + 确认按钮
    - 自定义输入 → 文本输入提示
  - 已选值预览
- 交互：
  - 点击选项 → 保存选择 → 自动前进到下一字段
  - 点击返回 → 回到上一字段
  - 点击跳过 → 前进但不填值（仅非阻塞字段）
  - 全部完成 → 进入确认页 → 提交
- 防重入：已通过 step_token + field + message_id 三重校验实现

### 5.3 极速画像入口（QuickProfileEntry）

- 位置：无画像时的入口层主操作区
- 类型：cl.Message + cl.Action
- 职责：只收集 3 个硬阻塞字段
- 字段顺序：目标 → 周跑量 → 可用训练日 → 确认
- 完成后自动触发计划生成

### 5.4 增量补全入口（FieldCompletionEntry）

- 位置：计划生成后、或工作流返回 missing_fields 时
- 类型：cl.Action 按钮组
- 职责：每次只提示当前缺失的字段
- 交互：逐字段补充，每填完一个自动推进到下一个

### 5.5 画像编辑入口（ProfileEditor）

- 位置：跑者身份卡的编辑按钮
- 类型：CustomElement（React 组件，Dialog/Sheet）
- 职责：训练中手动修改画像
- 展示：当前所有字段值 + 编辑区
- 修改后触发 FastAPI 写盘 + 状态刷新

### 5.6 自然语言感知提示（NLPExtractionHint）

- 位置：用户在聊天中说训练相关的话时
- 类型：cl.Message 小提示
- 职责：告知用户系统已从对话中自动提取了某些画像变化
- 示例："检测到你的周跑量可能已提升到 40km，已自动更新画像。"
- 始终需要用户确认才真正生效

## 6. 交互流程

### 6.1 完整画像填写

```text
[入口层引导] → [开始填写画像]
              → ProfileStepper：经验水平
              → ProfileStepper：目标
              → ProfileStepper：比赛日期
              → ProfileStepper：VO₂max
              → ProfileStepper：周跑量
              → ProfileStepper：LTHR
              → ProfileStepper：T配速
              → ProfileStepper：配速偏好
              → ProfileStepper：可用训练日
              → ProfileStepper：最长训练时长
              → ProfileStepper：地形偏好
              → ProfileStepper：训练类型偏好
              → ProfileStepper：备注
              → [确认页] → [提交] → 自动触发计划生成
```

### 6.2 极速画像

```text
[入口层引导] → [快速生成计划]
              → QuickProfileEntry：目标
              → QuickProfileEntry：周跑量
              → QuickProfileEntry：可用训练日
              → [确认] → 自动触发计划生成
```

### 6.3 增量补全（计划生成后发现缺失增强字段）

```text
[计划已生成] → [系统提示：补充 LTHR 可获得更精准的心率区间]
              → FieldCompletionEntry：LTHR
              → [提交] → 刷新画像 + 提示可重新生成计划
```

### 6.4 训练中手动编辑

```text
[跑者身份卡] → [点击编辑]
              → ProfileEditor 弹出（CustomElement Dialog）
              → 修改字段
              → [保存] → FastAPI 写盘 → 刷新身份卡 + 可选重新生成计划
```

### 6.5 自然语言自动提取

```text
[用户在聊天中说] "我最近跑量加到 50km 了"
              → LLM NLP 提取 → 检测：weekly_mileage 可能变为 50
              → NLPExtractionHint："检测到你的周跑量可能已提升到 50km，要更新画像吗？[确认] [忽略]"
              → [用户确认] → 自动更新 → 刷新身份卡
```

## 7. 状态设计

### 7.1 填写态

- 正在填写画像向导中
- 进度条明确展示当前位置
- 可返回、可跳过（部分字段）

### 7.2 完成态

- 画像已完整：展示跑者身份卡（含 LTHR 九区）
- 画像部分完整：展示核心指标 + 补充提示

### 7.3 空态

- 从未填写：展示画像引导，区分"完整填写"和"极速填写"两个入口
- 计划需要但缺字段：展示逐字段补全入口

### 7.4 异常态

- 无法从磁盘加载画像：使用默认画像 + 提示用户填写
- LTHR 为空：不展示心率区间，展示设置引导
- 自动计算区间异常：展示原始值而不展示错误区间

## 8. 与后端 / 会话数据关系（Option A 架构）

### 8.1 FastAPI 端点（应用层）

| 端点 | 方法 | 职责 |
|------|------|------|
| `/profile/{user_id}` | GET | 获取完整用户画像 |
| `/profile/{user_id}` | PUT | 更新用户画像（全量或部分） |
| `/profile/{user_id}/zones` | GET | 获取 LTHR 九区和配速区间（每次从画像衍生） |
| `/profile/{user_id}/fields/{field_key}` | PATCH | 更新单个画像字段 |
| `/profile/{user_id}/nlu-extract` | POST | 从自然语言文本中提取画像字段（返回建议变更，不直接写盘） |

### 8.2 Chainlit 层职责（展示层）

- 调用 FastAPI 端点获取画像数据
- 用 CustomElement + Action 渲染画像 UI
- 接收用户填写/编辑 → 调用 FastAPI 写盘
- 不直接操作 `user_profile.json` 文件

### 8.3 数据流

```text
[Chainlit UI] ──GET──→ [FastAPI /profile] ──读──→ [user_profile.json]
                                                   │
[Chainlit UI] ──PUT──→ [FastAPI /profile] ──写──→ [user_profile.json]
                              │
                              └── 自动 sync_user_zones()
                              └── 更新 LangGraph state
```

### 8.4 当前代码与目标架构的差距

| 当前实现 | 目标架构 | 差距 |
|------|------|------|
| Chainlit 直接读写 `user_profile.json` | FastAPI 端点封装读写 | 新增 FastAPI 画像端点 |
| Wizard 逻辑在 `wizard_logic.py` | Wizard 渲染逻辑保留，数据操作走 FastAPI | 把 `save_user_profile()` 调用替换为 FastAPI 调用 |
| 侧边栏直接读 `state.user_profile` | 走 FastAPI 端点或会话态缓存 | 增加统一数据来源 |

## 9. Chainlit 落地方式

### 9.1 利用 Chainlit 原生能力

- **Actions**：画像向导中的选项按钮（已实现）
- **Messages**：Progress 指示、字段说明文案（已实现）
- **CustomElement**：跑者身份卡（新增，替代当前侧边栏纯文本）
- **Dialog / Sheet**：画像编辑器弹出（新增，替代当前只能聊天区编辑）

### 9.2 落地步骤建议

1. **Phase 1**：新增 FastAPI 画像端点（GET/PUT/PATCH/NLU-extract）
   - 把 `profile_store.py` 的逻辑暴露为 REST 端点
   - 同步 `sync_user_zones()` 逻辑

2. **Phase 2**：新建跑者身份卡 CustomElement
   - 替代当前侧边栏的纯文本画像区
   - 文件：`public/elements/RunnerIdentityCard.jsx`
   - 用 Card + Badge + Progress + Accordion 组件
   - Accordion 展开 LTHR 九区详情

3. **Phase 3**：新建画像编辑器 CustomElement
   - 文件：`public/elements/ProfileEditor.jsx`
   - 用 Sheet/Dialog 弹出
   - 字段按分组展示，支持就地编辑
   - 编辑后调用 FastAPI 写盘

4. **Phase 4**：向导逻辑迁移
   - 将 `save_user_profile()` 替换为调用 FastAPI
   - 保留 Wizard 逐字段引导体验（已在 Chainlit Actions 中验证良好）

### 9.3 现有良好体验保留

- 逐字段步进引导 → **保留**，体验已验证良好
- 进度指示 → **保留**
- 极速/完整/增量三种模式 → **保留**
- NLP 自动提取 → **保留**，增加确认步骤
- 防重入机制 → **保留**

## 10. 与其他模块的关系

画像层直接驱动：

- **入口层**：画像完整性决定入口展示内容（画像引导 vs 工作台）
- **训练计划层**：画像决定周期、强度、训练结构、可用日分配
- **关键解释层**：解释为什么给某用户安排某训练（如 "因为你的目标是全马 sub330..."）
- **证据可信层**：画像辅助筛选相关证据
- **训练反馈层**：反馈触发画像自动修正
- **数据状态层**：画像影响恢复/风险/负荷判断的阈值

## 11. 暂不设计的内容

- 具体颜色和字号
- 跑者身份卡的完整视觉稿
- ProfileEditor 的表单具体布局
- 画像历史版本管理
- 多用户画像切换（当前仅支持 default_user）

## 12. 后续确认重点

- 跑者身份卡放在哪里：Chat 区置顶消息 vs 侧边栏 vs 独立面板
- 画像编辑器是全屏 Sheet 还是居中 Dialog
- NLP 自动提取的变更是否需要用户手动确认（暂定：需要）
- LTHR 九区在卡片中有多详细（仅标签 vs 展开含具体数值）
- "补充增强字段可获得更个性化计划"的提示频率控制
