# 证据可信层设计（产品级细化版）

## 1. 文档目的

本文档定义马拉松助手证据可信层的产品级设计。证据可信层负责把 RAG、GraphRAG 和 Decision Graph 的证据能力转化为用户能感知的可信体验——让用户知道"这条建议不是随便说的，背后有据可查"。

## 2. 模块定位

证据可信层是马拉松助手区别于普通训练 App 和普通聊天机器人的关键能力。

它不只是显示引用编号，而是让用户感知到三层可信：
- **来源可信**：知道证据来自哪里（论文 / 训练模板 / 经验规则）
- **内容可信**：能看到原文摘录，不用离开页面去翻论文
- **关系可信**：知道这条证据和当前建议有什么关系

## 3. 用户场景

### 3.1 场景 A：看到引用编号，想验证

用户在训练计划解释中看到 `[1]` `[3]`，好奇这些引用指向什么。

用户此时的困惑：
- [1] 是什么来源？
- 原文说了什么？
- 这条证据和我的训练直接相关吗？

证据可信层需在此场景提供"点击编号 → 看原文摘录 → 关闭"的轻量体验。

### 3.2 场景 B：想深入了解证据

用户对某个训练方法感兴趣，想看完整的证据。

用户此时的困惑：
- 这篇论文还说了什么？
- 我能看到完整的证据页吗？
- PDF 原文在哪里？

证据可信层需在此场景展示来源文件名、页码、完整摘录。

### 3.3 场景 C：没有证据

用户看到一条训练建议，但没有引用编号。

用户此时的困惑：
- 这条建议没有依据吗？
- 系统是否在编造？

证据可信层需在此场景明确告知"当前建议暂无直接证据来源"，不做假引用。

## 4. 信息架构

证据可信层分两级展示：

### 4.1 第一级：轻量编号（嵌入上下文）

```text
正文中的引用：
"...由于过度训练会导致 VO₂max 下降 `[1]`，建议本周降低强度..."
"...间歇跑对提升 VO₂max 有显著效果 `[1]``[2]`..."

格式：灰色 inline code badge `[1]``[2]`
已实现：output_nodes.py _format_evidence_suffix()
```

### 4.2 第二级：证据抽屉（EvidenceDrawer）

```text
证据抽屉
├── 证据编号 + 来源文件名（如 "[1] 2016 - Nutrition for Marathon Running.pdf"）
├── 页码（如 "第 42-45 页"）
├── 原文摘录（如 "Long runs should be performed at 60-70% of VO₂max..."）
├── 证据类型标签（科研论文 / 训练模板 / 经验规则）
├── 与此建议的关系（如 "该证据支持本周长距离跑安排在 Z2 区间"）
└── 操作：[查看完整证据列表] [关闭]
```

## 5. 组件拆分

### 5.1 证据编号徽章（EvidenceBadge）

- 位置：解释文本、训练卡片中的任何引用处
- 类型：CustomElement（简单 span / Badge）
- 职责：在正文中标记引用，可点击
- 格式：`[1]` → 灰色 inline code 风格（已实现）
- 交互：点击 → 弹出 EvidenceDrawer
- 空态：无证据时不渲染任何编号

### 5.2 证据抽屉（EvidenceDrawer）

- 位置：浮层
- 类型：CustomElement（React 组件，Dialog / Sheet）
- 职责：展示一条或多条证据的详细信息
- 触发：点击 EvidenceBadge 或"查看证据"按钮
- 每条证据展示：
  - 编号（如 `[1]`）
  - 来源文档名
  - 页码范围
  - 原文摘录（截取关键段落，不是全文）
  - 证据类型 Badge
  - 与当前建议的关系说明（如果可映射）
- 多条证据时：垂直排列，可分页
- 底部操作：
  - "查看所有证据" → 展开完整证据列表
  - "关闭"
- 可移植性：纯数据驱动 props

### 5.3 证据关系说明（EvidenceRelationNote）

- 位置：EvidenceDrawer 每条证据下方
- 类型：文本行
- 职责：告诉用户这条证据和当前训练建议的具体关系
- 示例：
  - "该证据支持本周长距离跑安排在 Z2 区间"
  - "该证据支持节奏跑的配速建议"
  - "该证据为间歇跑的组间休息时间提供参考"
- 数据来源：如果无法映射关系，显示"该证据为训练安排提供参考依据"

### 5.4 缺证据提示（NoEvidenceNote）

- 位置：训练解释或建议下方（当无证据时）
- 类型：小字体文本
- 职责：诚实告知无直接证据
- 内容："当前建议基于训练知识图谱推导，暂无直接论文证据"
- 设计原则：不隐藏、不伪造、不让用户失去信任

### 5.5 查看证据按钮（ViewEvidenceButton）

- 位置：DailyWorkoutDetailCard 操作区、ExplanationDrawer 底部、QA 回答底部
- 类型：按钮
- 职责：统一证据入口
- 已有：`legacy_ui.build_evidence_preview_bundle()` 生成的按钮（已实现）

## 6. 交互流程

### 6.1 从引用编号查看证据

```text
[正文中的 `[1]``[2]`] → [用户点击 `[1]`]
                       → 弹出 EvidenceDrawer
                       → 展示证据 #1 的详细信息
                       → 用户可：
                           ├── 阅读原文摘录
                           ├── 点击下一条证据（如有多条）
                           ├── 点击"查看所有证据" → 展示完整证据列表
                           └── 关闭抽屉
```

### 6.2 从训练解释查看证据

```text
[ExplanationDrawer] → [底部证据标签栏：`[1]` `[2]` `[3]`]
                    → 点击任一编号 → EvidenceDrawer 弹出对应证据
```

### 6.3 从 QA 回答查看证据

```text
[QA 回答中的引用 `[1]`] → [点击] → EvidenceDrawer
                                   → 已通过 build_evidence_preview_bundle 生成按钮
                                   → 支持 `[来源: xxx.pdf]` 兼容解析（fallback 已实现）
```

### 6.4 无证据场景

```text
[训练建议 / 解释] → 无 EvidenceBadge → 自动展示 NoEvidenceNote
                                        → 不生成虚假引用
```

## 7. 状态设计

### 7.1 有证据态

- EvidenceBadge 可点击
- EvidenceDrawer 正常展示
- evidence_base 完整可用

### 7.2 部分证据态

- evidence_base 有数据，但某些训练解释的 evidence_ids 缺失
- 对应解释处不显示 EvidenceBadge
- 不全局报错

### 7.3 无证据态

- evidence_base 为空或无匹配
- 所有引用处不显示编号
- 展示 NoEvidenceNote

### 7.4 异常态

- evidence_ids 指向的 ID 在 evidence_base 中不存在：编号仍显示但灰显不可点击
- `[来源: xxx.pdf]` 格式无法匹配到 evidence_base：不生成 EvidenceBadge（已实现兼容解析）
- evidence_base 格式异常：降级为空证据，不崩溃

## 8. 与后端 / 会话数据关系（Option A 架构）

### 8.1 消费的数据结构

证据可信层从 `structured_report` 中消费：

| 数据 | 来源字段 | 用途 |
|------|------|------|
| 证据详情 | `evidence_base[]` | EvidenceDrawer 全部内容 |
| 证据编号 | `item.evidence_ids` | EvidenceBadge 渲染 |
| 来源文档 | `evidence_base[].source` | 证据抽屉来源展示 |
| 页码 | `evidence_base[].pages` | 页码范围 |
| 原文 | `evidence_base[].text` | 原文摘录 |
| 证据类型 | `evidence_base[].doc_type` 或推理 | 证据类型 Badge |

### 8.2 FastAPI 端点（应用层，新增建议）

| 端点 | 方法 | 职责 |
|------|------|------|
| `/evidence/{evidence_id}` | GET | 获取单条证据详情 |
| `/evidence/batch` | POST | 批量获取证据（传入 evidence_ids 列表） |

### 8.3 Chainlit 层职责（展示层）

- 渲染 EvidenceBadge（已在 `_format_evidence_suffix()` 实现）
- 点击后调用 FastAPI 获取证据详情
- 以 EvidenceDrawer 展示
- 处理 `[来源: xxx.pdf]` 兼容解析（已在 `build_evidence_preview_bundle` 实现）

## 9. Chainlit 落地方式

### 9.1 利用 Chainlit 原生能力

- **CustomElement（Dialog / Sheet）**：EvidenceDrawer
- **Markdown inline code**：EvidenceBadge（已实现）
- **Actions**：查看证据按钮（已实现）

### 9.2 CustomElement 文件规划

| 文件 | 组件 | 接收 props |
|------|------|------|
| `public/elements/EvidenceDrawer.jsx` | EvidenceDrawer | `evidence_items[]`（每项含 id、source、pages、text、doc_type、relation_note） |

### 9.3 落地步骤建议

1. **Phase 1**：新建 FastAPI 证据端点
   - `/evidence/{evidence_id}` GET
   - `/evidence/batch` POST

2. **Phase 2**：新建 EvidenceDrawer CustomElement
   - 替代当前纯文本证据预览
   - 用 Card + Badge + ScrollArea

3. **Phase 3**：统一证据点击链路
   - EvidenceBadge 点击 → EvidenceDrawer
   - "查看证据"按钮 → EvidenceDrawer
   - QA 引用 → EvidenceDrawer

### 9.4 现有良好体验保留

- `[1]` 的 inline code 格式 → **保留**
- `build_evidence_preview_bundle()` → **保留**，内部改为调用 FastAPI
- `[来源: xxx.pdf]` 兼容解析 → **保留**
- 无证据时不伪造引用 → **保留**

## 10. 与其他模块的关系

证据可信层是可信度提供方，被以下模块消费：

- **关键解释层** → 解释中的证据入口
- **训练计划层** → 训练卡中的证据入口
- **问答层（QA）** → 回答中的引用溯源
- **数据状态层** → 风险和恢复判断的证据支撑

## 11. 暂不设计的内容

- 证据的完整 PDF 预览（需 PDF Viewer 集成）
- 证据质量的自动评分
- 证据的新鲜度/过时检查
- 用户对证据的反馈（"这条证据有帮助/无帮助"）

## 12. 后续确认重点

- EvidenceDrawer 用 Dialog 还是 Sheet
- 原文摘录截取多长（当前建议 3-5 句）
- 证据类型标签（科研论文/训练模板/经验规则）的数据来源
- "查看所有证据"是一个独立页面还是列表弹窗
