# 马拉松助手 — C 端上线就绪度评估

> 评估日期：2026-06-13
> 评估范围：面向公众 C 端产品形态
> 评估方式：后端源码静态审计（apps/backend/src/marathon_qa_assistant/）
> 重点维度：安全合规 · 稳定性 · 工程就绪度 · 成本

---

## 一句话结论

工程成熟度远高于典型项目，已具备生产级骨架（鉴权、限流、配置门禁、可观测性、容器化、CI）。但作为**会输出训练/医疗相关建议的 C 端产品**，上线前仍有 **5 个 P0 必修项**和若干 P1 项需要补齐，核心集中在「医疗合规的法律边界」「LLM 调用韧性」「真实负载验证」三处。

**建议路径**：先做有限灰度（邀请制/白名单），并行补齐 P0，再开放公众注册。

## 维度一：安全与合规

### 技术安全（🟢 已具备）

**医疗安全门 — 真实有效**
`nodes/security.py` 内置医疗风险关键词库（`_scan_medical_risk`），命中严重红旗（心脏症状、应力性骨折征兆、跟腱断裂等）会**立即拦截、拒绝生成训练计划**，并按症状给出分科室就医指导（心内科 / 骨科 / 运动医学科）。这是 C 端医疗类产品最关键的安全设计，已落地。

**输入 / 输出双向防护**
`security.py`（525 行）实现 InputGuard（prompt 注入、越狱、API key 泄露检测，覆盖最近 6 轮历史）+ OutputGuard（敏感信息脱敏、有害内容拦截）。检索内容拼进 prompt 前经过 `scan_and_clean_context()` 清洗，prompt 带安全后缀防止 KB 内容里的指令被执行。

**KB 权限标记被消费**
`prescription_permission` / `exclude_from_training_generation` / `referral_and_flag_only` 在 expert_nodes、profile_and_retrieval、evidence_chain 等多处被实际读取，sport_psychology / medical_safety 的 explanation_only / referral_only 约束不会污染训练处方生成。

### 合规缺口（🟡 上线前必处理）

| # | 项目 | 风险 | 优先级 |
|---|------|------|--------|
| C1 | **医疗免责声明的法律充分性** | 代码里有免责文案（response_builders.py），但是否满足 C 端医疗类产品的法律要求，需法务/合规审阅。免责措辞、展示位置（是否每次输出都可见）、用户是否需主动确认，都要定。 | **P0** |
| C2 | **未成年人门禁** | 未发现强制年龄校验。马拉松训练对未成年人有特殊生理风险（骨骺、RED-S），且法律上未成年人数据处理有额外要求。需在注册/使用前加年龄确认，对未成年用户限制或拒绝服务。 | **P0** |
| C3 | **用户隐私与数据合规** | 用户档案含身体/健康数据（属敏感个人信息）。需确认：存储是否加密、是否有隐私政策、是否有收集使用同意流程、是否符合《个人信息保护法》对敏感信息的「单独同意」要求。 | **P0** |
| C4 | **用户协议 / 服务条款** | C 端产品需要用户协议明确责任边界（"本产品提供的训练建议不构成医疗诊断，用户需自行判断身体状况"）。 | **P0** |

> 注：C1–C4 偏法律而非技术。建议在灰度阶段并行推进，找一次法务/合规咨询一次性过完。

## 维度二：稳定性与降级

### 已具备（🟢）

- **限流中间件**：`_rate_limit_middleware` 基于客户端+路由的滑动窗口限流，默认 600/分钟，超限返回 429 + Retry-After。
- **降级骨架**：`FallbackIntegratedApp`（LangGraph 不可用时按节点串行兜底）、BM25 fallback（FAISS 挂掉时的检索降级）、`workflow_error` 兜底节点。
- **LLM 超时配置**：`LLM_TIMEOUT_SEC` 默认 60 秒。

### 需验证 / 补齐（🟡）

| # | 项目 | 风险 | 优先级 |
|---|------|------|--------|
| S1 | **LLM 调用重试缺失** | 仅有超时，未见明确的失败重试/退避逻辑。DeepSeek/OpenAI 网关偶发 5xx（本次评估中网关就出现过 503），无重试会直接让用户请求失败。建议加 2–3 次指数退避重试。 | **P0** |
| S2 | **降级路径的真实可用性** | fallback 设计存在，但「Ollama 挂掉 / 向量库加载失败 / 某专家节点 LLM 失败」时，端到端是否真能返回有意义降级结果，需用故障注入实测，不能只看代码不报错。 | **P1** |
| S3 | **请求级超时** | 多专家串行调用 LLM，加上最多 2 次审计重试循环，最坏情况单请求可能很慢。需确认有请求级总超时，避免连接 hang 死耗尽资源。 | **P1** |
| S4 | **审计重试的成本/延迟放大** | rule_checker → llm_critic → 最多重试 2 次回生成层，最坏一次请求把生成链跑 3 遍。需确认重试预算被严格限制（代码中 `iteration >= 2` 有控制，需确认无死循环可能）。 | **P1** |

## 维度三：工程就绪度

### 已具备（🟢 — 这是项目的强项）

- **容器化**：多阶段 Dockerfile，非 root 用户（marathon）运行，runtime 镜像精简。
- **CI**：`.github/workflows/ci.yml`，ruff lint + pytest + coverage，PR 触发，并发取消。
- **配置外置 + 生产门禁**：`settings.py` 全量环境变量化；生产环境强制 `MARATHON_API_TOKEN` + `MARATHON_FERNET_KEY`，缺失直接 503 拒绝启动服务（`runtime_config_errors`）。
- **密钥管理**：Fernet 加密，日志 `redacted()` 脱敏，无明文 sk- 密钥泄露。
- **可观测性**：`observability.py`，请求级 request_id、耗时记录、token 用量追踪。
- **健康检查**：`/health`（公开）+ `/admin/health`（鉴权，含 KB/DB/Ollama/模型详情）。
- **依赖锁版本**：`constraints.txt` 精确钉版本。
- **测试规模**：97 个测试文件，覆盖安全卡片、计划校验、证据链、数据库事务、XSS 契约等。

### 需补齐（🟡）

| # | 项目 | 风险 | 优先级 |
|---|------|------|--------|
| E1 | **CI 质量门禁偏松** | ruff 只查 `E,F,W` 且忽略 E501；coverage 有采集但未见失败阈值。建议设最低覆盖率门槛（如关键模块 ≥70%），lint 逐步收紧。 | **P2** |
| E2 | **真实负载/压测缺失** | 有限流配置但无压测数据。C 端开放前需做并发压测，确认限流参数、LLM 网关并发上限、单实例吞吐。 | **P1** |
| E3 | **依赖编排文档** | Ollama（embedding）+ 向量库 + 可能的 DB 的部署编排需要一份清晰 runbook，避免部署到服务器跑不起来。 | **P2** |
| E4 | **监控告警闭环** | 有 observability 数据采集，但是否接入告警（错误率、延迟、LLM 失败率、成本异常）需确认。 | **P1** |

## 维度四：成本

### 实际模型选型（关键事实）

代码实际默认用：
- **DeepSeek-v4-pro**（主力 LLM provider，`LLM_PROVIDER=ds`）
- **GPT-5.5**（OpenAI 兼容备选）
- **Ollama qwen2.5:latest**（本地）+ **bge-m3**（本地 embedding）

**不是**架构设计文档里写的 Anthropic Opus/Sonnet。这是个好消息：DeepSeek 单价比 Opus 低一两个数量级，本地 Ollama 部分零边际成本。

### 成本结论（🟢 可控）

- 单次「生成训练计划」请求会串行调用多个专家节点 + 审计 critic，最坏含 2 次重试，估算单请求 LLM 调用 5–15 次。
- 以 DeepSeek 价位，单次完整计划生成的 LLM 成本量级很可能在**人民币几分到几毛**区间（精确值需用真实 prompt token 量实测）。
- embedding 走本地 Ollama，无 API 成本。
- **主要成本风险点**：审计重试循环的放大、以及未来若切回高价模型。建议保留 `token_usage` 统计并接入成本监控告警。

> 待办：用真实请求采一次端到端 token 用量，把成本从「量级估算」变成「精确单价」。
